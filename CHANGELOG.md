# Changelog

All notable changes to MediaVault are documented in this file.

## [4.70.0] — Use Episode History to Resolve Ambiguous TV Show Matches

- **Root problem**: title/metadata scoring alone can't tell apart two TV series that share an identical title (e.g. the animated *Avatar: The Last Airbender* vs. the live-action remake) — both score identically on title similarity, and with no reliable air-year in the imported data, year scoring doesn't separate them either. Previously this fell straight to popularity as the tie-breaker, which can just as easily land on the wrong one (a newer live-action remake is often *more* popular right now than a decade-old animated original), producing an import that then fails every later "no matching episode found on TMDB" for every episode beyond what the wrong show actually has.
- **Milestone 1 — episode-based candidate validation**: added `scoreEpisodeHistoryFit()` in `tmdb-match.ts`, which compares imported `(season, episode)` pairs against a candidate's real TMDB season list (season number + episode count per season, from `TMDBService.getTV().seasons`). An imported episode only "matches" a candidate if that season exists in its catalogue *and* the episode number is within that season's episode count — which inherently folds in all four requested comparisons (season numbers, episode numbers, total seasons, total episodes) in one pass, since a candidate with fewer seasons/episodes than the import simply can't explain the higher ones.
- **Milestone 2 — whole-history scoring**: the fit score is computed over *every* imported watch for that series, not a single episode — `matched / total` across the full imported history, so a candidate explaining every season and episode always outscores one that only coincidentally matches the title.
- **Milestone 3 — pipeline integration**: this is a new step inside `findBestMatch()`, slotted in exactly where the milestone specifies — after title/year/country/language/metadata scoring has already picked a tier (`exact`/`year`/`fuzzy`) and identified a genuine top-of-ranking tie, and *before* the popularity tie-break added previously. Nothing about the existing scoring algorithm (`scoreCandidate()`), tier thresholds, or the "clear winner never gets overridden" behavior changed — episode history is consulted only when `tieGroup.length > 1`, exactly like popularity was. If episode history is unavailable (movies, or a series with no imported episode watches yet) or produces no decisive result (best fit doesn't beat the runner-up by at least `0.2`), resolution falls through to popularity exactly as before — so behavior for every case outside a genuine identically-scored TV tie is unchanged.
- **Milestone 4 — diagnostics**: `MatchTier` gained a new `"episode-history"` value alongside `exact`/`year`/`fuzzy`/`popularity`/`unmatched`, with a corresponding `tieBrokenByEpisodeHistory` flag on `MatchResult`/`MatchLogEntry`. `ImportReport` gained `episodeHistoryMatchCount`, surfaced as its own "Episode-history validated matches" row in the import report, alongside the existing Exact/Metadata-assisted/Popularity-tie-break/Unmatched counts — so it's visible exactly which resolution method picked a given series.
- **Wiring**: `MediaResolver` now accepts an `episodeHistoryByKey` map (built once in `collectDistinctResolutions()` from every `series`-kind watch's `seasonNumber`/`episodeNumber`, keyed identically to the existing per-title resolution cache key) and threads the matching series' full imported episode list into `findBestMatch()`, along with a `fetchCandidateSeasons()` fetcher backed by the already-cached `TMDBService.getTV()` — so re-checking the same candidate's season list across multiple ambiguous imports in one run costs nothing extra.
- Matching stays fully deterministic and idempotent: the same imported history and the same TMDB responses (cached) always produce the same tie-break decision on re-import.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written (none exist in this source tree to patch either).

## [4.69.0] — Improve Ambiguous Import Matching

- **Milestone 1 — popularity as final tie-breaker**: `findBestMatch()` keeps its existing title/year/region scoring algorithm completely unchanged. After scoring, candidates whose composite score lands within `0.03` of the top score now form a "tie group." When that group has more than one member, the winner is chosen by TMDB popularity (highest first) instead of arbitrary array order — previously, genuinely ambiguous candidates that individually scored high enough to be valid matches could still get selected somewhat arbitrarily by sort order with no signal used to break the tie.
- **Milestone 2 — strong matches untouched**: popularity is only consulted for candidates already inside the tie group — it never contributes to `scoreCandidate()` and never promotes a low-scoring candidate over a clear title/year/region winner. If the top-scored candidate has no other candidate within the tie margin, resolution is identical to before (same tier, same candidate, same behavior for `exact`/`year`/`fuzzy`/`unmatched`). Items that fail the existing `fuzzy` threshold (`score < 0.55`) are still reported unmatched — popularity is never used to rescue a low-confidence match, only to choose between multiple already-valid candidates.
- **Milestone 3 — diagnostics**: added a new `MatchTier` value, `"popularity"`, alongside the existing `exact`/`year`/`fuzzy`/`unmatched`, plus a `tieBrokenByPopularity` flag on `MatchResult`/`MatchLogEntry` so the console match log can distinguish a genuine popularity-broken tie from an ordinary metadata match. `ImportReport` gained `exactMatchCount`, `metadataMatchCount` (rolls up `year` + `fuzzy`, both already metadata-assisted tiers), `popularityTieBreakCount`, and `unmatchedMatchCount`, all surfaced as new rows in the import report's diagnostics section (Exact matches / Metadata-assisted matches / Popularity tie-break matches).
- `TMDBSearchResult` gained a `popularity` field (from TMDB's `popularity` search-response field, defaulting to `0` when absent), threaded through `normalizeSearchResult()` — the only place `TMDBSearchResult` objects are constructed, so no other call site needed touching.
- Matching remains fully deterministic: TMDB search results are cached per query, `Array.prototype.sort` is stable, and popularity tie-breaking uses a fixed, reproducible comparator — the same archive re-imports to the same resolutions every time.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written (none exist in this source tree to patch either).

## [4.68.0] — Fix Import Progress Reporting

- **Root cause**: the import progress modal genuinely was receiving progress callbacks, but only from the tail end of `commitBundle()` — the "Applying watch history/comments/likes/ratings/favorites/lists" loops. The two phases that actually dominate a large GDPR import's wall-clock time had **no progress reporting at all**: resolving every distinct title against TMDB (`Media matching (total)`, one network round-trip per unique movie/show) and fetching each matched show's full episode catalogue (`Episode importing (catalogue fetch)`). For a library with thousands of distinct titles, the modal sat on "Starting…" for the entire duration of both phases before the counter ever moved. Parsing itself compounded this: `parseGdprArchive()` ran as one long fully-synchronous function processing every CSV file and every row with no callback and no yield point, so even once a callback existed there was nothing pumping the event loop to let the modal repaint.
- **Milestone 1 — real-time updates across every stage**: added explicit progress stages for every step of the pipeline — Reading ZIP, Extracting files, Parsing CSVs, Building lookup tables, Matching movies, Matching TV series, Matching episodes, Importing watch history, Importing rewatches, Importing ratings, Importing comments, Importing lists, Saving data, Finalizing — wired through `runZipImport()` → `parseGdprArchive()` → `commitBundle()` → `ImportModal`.
- **Milestone 2 — record-based progress**: the two previously-silent phases now report live `done / total` counts. Media matching ticks per distinct title resolved (throttled to ~10/sec so the DOM isn't hammered); episode catalogue fetch ticks per show once its episodes are imported; the large GDPR tracking-record parsing loops (`tracking-prod-records.csv` / `tracking-prod-records-v2.csv`, which can run into the tens of thousands of rows) now report "Matching episodes: N / total" every 25 rows instead of processing silently start-to-finish.
- **Milestone 3 — prevent UI freezing**: `parseGdprArchive()` is now `async` and yields to the event loop (`setTimeout(…, 0)` — a real macrotask boundary, not a microtask, so the browser actually gets to paint) at regular intervals inside every large synchronous loop: once per parsed CSV file, and every 200 rows inside the two big tracking-record loops. The commit-side matching and episode-fetch phases yield every 25 (resp. 5) completed items on top of their per-item `await`s. Yield frequency was tuned to be frequent enough to keep the modal responsive without adding measurable overhead to import throughput (a `setTimeout(0)` every 25–200 iterations, not every iteration).
- **Milestone 4 — accurate stage reporting**: every phase now announces its stage *before* doing any work (`onProgress(0, 1, "Matching movies & TV series")` etc.), so the modal transitions off "Starting…" the instant the commit actually begins, not once the first slow phase finishes. `runZipImport()`'s progress callback signature grew a `stage` parameter (previously `(done, total)`) so ZIP-reading/extraction stages show real labels instead of a generic "Scanning files" placeholder.
- Renamed the "Applying watch history/comments/likes/ratings/favorites/custom lists" stage labels shown in the modal to match the spec's stage vocabulary ("Importing watch history", "Importing comments", etc.) — cosmetic only, no behavior change to the underlying `timer.time()` breakdown labels used in the diagnostics report.
- Import remains fully idempotent — none of the above touches matching/merge/write logic, only when and how often progress is reported and where the event loop gets a chance to breathe.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written, per standing instruction.

## [4.63.1] — Fix Custom List Manual Drag Regression (iOS Feel, Android Not Working)

- **Root cause**: a prior Android drag fix added `touch-action: pan-y` to the single shared `.is-draggable` CSS class, which both platforms' cards carried. This is a plain TypeScript/DOM Obsidian plugin, not React Native — the drag mechanisms are native HTML5 `draggable`/`dragstart` on desktop/iOS and a hand-rolled `pointerdown`/`pointermove`/long-press implementation on Android (`setupAndroidManualDrag`), so a single CSS rule shared across both was the actual coupling bug:
  - **iOS**: `pan-y` fought WebKit's own long-press-based native-DnD gesture recognizer, making it noticeably harder to pick up a card.
  - **Android**: `pan-y` explicitly tells the browser it's free to treat any early vertical finger movement as a native scroll, firing `pointercancel` on the card before the 350ms long-press timer could ever complete — so the custom drag session was killed before it started, every time.
- **Fix**: split the shared class into two independent ones — `is-draggable` (native-DnD path, unchanged `cursor: grab`, no touch-action override, restoring the original pre-regression iOS feel) and `is-touch-draggable` (Android's pointer-capture path, `touch-action: none` from touch-start so the browser can't preempt the gesture, plus `-webkit-touch-callout`/`user-select: none` so Android's native long-press callout/context-menu can't hijack mid-gesture either — reinforced with a `contextmenu` preventDefault for the duration of the drag session). Gesture logic itself (long-press timing, move-cancel threshold, pointer capture, drop-target detection) was untouched — the bug was purely in touch-action scoping, not the gesture state machine.
- Trade-off, called out rather than hidden: Android manual-drag cards can no longer be used as a scroll-start point (a swipe beginning on a card no longer natively scrolls the grid, since `touch-action: none` is sampled once at touch-start for the whole gesture); scrolling still works starting from any non-card area. This is the standard, accepted trade-off for reliable long-press-drag-to-reorder on touch and matches the platform-specific, no-compromise approach requested.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written, per standing instruction.

## [4.63.0] — TV Time GDPR List Import: Root-Caused Lists Collapsing to One

- **Root cause**: `lists-prod-lists.csv` parsing/merge/persistence all correctly handled multiple rows, but every list's identity — both for the initial import and for idempotent re-import matching — was keyed off the list's mutable display `name` (`applyList` matched existing lists via `importSource === list.name`). TV Time's own default lists commonly share a generic display name across a user's account (e.g. multiple lists literally named "Watchlist"), so any two same-named lists in the export silently merged into a single MediaVault list instead of staying distinct. Two compounding bugs in `gdpr.ts`'s row loop made this worse: a row was skipped entirely (`continue`) whenever its parsed item count was zero — dropping legitimately empty lists and any list whose items all failed to resolve — and a row with a blank `name` was also skipped outright rather than falling back to a usable label, discarding lists TV Time exports without a custom name.
- **Fix**: `ListImport` now carries a stable `sourceKey`, built from TV Time's own per-list `s_key` slug (falling back to a name-derived key only when `s_key` is absent). `applyList` matches existing lists by `sourceKey`, not `name`, so same-named-but-distinct lists never collapse, and re-importing the same archive updates the matched list in place (including picking up a renamed title/description) instead of duplicating. The row loop no longer drops a list for having zero items or a blank name — a blank `name` now falls back to a slug-derived label (or `Imported List N` as a last resort), and every list row is preserved regardless of how many of its items resolved.
- **Item-level diagnostics**: list items that parse but carry no `id`/`uuid` are no longer silently dropped from the count — the importer now emits a warning per list summarizing how many of its items couldn't be identified, consistent with every other importer path's unresolved-item reporting.
- **Parser hardening**: `parseGoMapArray` no longer assumes TV Time's Go `fmt %v` map syntax is the only shape the `objects` column can take — it now falls back to parsing the column as a plain JSON array when no `map[` token is present, so a format difference in a given export can't silently yield zero items for an otherwise-valid list. Item ordering is preserved in both paths.
- `JsonListImporter` (the non-GDPR JSON list import path) also gained a `sourceKey` (the list's own `id` when present, else name-derived) for the same reason, with no behavior change for exports that don't collide on name.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written, per standing instruction.

## [4.54.0] — Fix Detail Modal Re-render After Watch History Exists

- **Root cause (genre translation blocking mid-render)**: `renderHero()` awaited the TMDB genre-translation lookup *after* the title/favorite button were already appended to the live DOM. When that lookup wasn't yet cached (a real network call), the browser could paint a half-built modal before the rest of the header arrived a frame later. Fixed by resolving genre names before any DOM mutation begins — `render()` now gathers all header data first, then performs `contentEl.empty()` + full rebuild as a single synchronous block, so the header can never be split across two paint frames.
- **Root cause (per-episode-row async fragmentation)**: `renderEpisodesTab` rendered every episode row via `Promise.all`, with each row individually awaiting its own `episodeWatches.findByEpisodeId()` call — a separate async suspension point per row. For a show with zero watched episodes no season auto-expands, so this was invisible; but once any episode is marked watched, its season auto-expands on open, making a whole season's worth of individually-fragmented row renders visible at once. Fixed by batch-fetching all of a show's `EpisodeWatch` records once via `findByMediaId`, grouping them into a map, and making `renderSeason`/`renderEpisodeRow` fully synchronous — no per-row awaits remain in the render path.
- Together these remove every unnecessary async gap between modal-open and full content paint, so the presence (or size) of a title's watch history no longer affects how the detail modal opens.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No new tests written, per standing instruction.

## [4.43.0] — Direct Close-Button Removal, Scoped Per-Modal

- Replaced every prior CSS/global-observer/lifecycle-gate approach with the simplest correct fix: `modal.modalEl.querySelector(".modal-close-button")?.remove()` called immediately when each MediaVault modal builds its chrome, plus a `MutationObserver` scoped strictly to that modal's own `modalEl` (not `document.body`, not a shared/global observer) so the button is removed again after every re-render. Disconnected in a wrapped `onClose` to avoid leaking observers.

The default close button started appearing once the mobile-header/back-button milestones (v4.2x–v4.33) gave modals real header chrome — it's a side effect of that UI work, not a single reverted line, so there's no old code path to restore; removing the button explicitly (as done here) is the correct fix rather than a workaround.

## [4.42.0] — Modal Close Button: Lifecycle-Gated Fix

- **Actual root cause**: every prior attempt (CSS descendant selector, per-modal `MutationObserver`, body-level `MutationObserver` keyed off a container relationship) made an assumption about *where* Obsidian places `.modal-close-button` relative to a MediaVault modal's own DOM. Each assumption held on some platform/version and broke on another, which is why the button kept reappearing after every fix — the bug was in guessing DOM shape at all, not in any particular guess.
- Replaced all DOM-shape guessing with a lifecycle-based gate: MediaVault now tracks its own open modals directly (added to an `openMediaVaultModals` set in `markMediaVaultModalShell`, removed via a wrapped `onClose`). Obsidian only ever shows one modal on top at a time, and MediaVault never opens a native Obsidian modal from inside one of its own, so "one of our modals is currently open" is a fact we can track with certainty instead of inferring from markup.
- While that set is non-empty, any `.modal-close-button` found anywhere in the document gets suppressed via a direct inline `style.setProperty("display", "none", "important")` — not a stylesheet rule — so it can't lose a CSS specificity/cascade-order fight against Obsidian's own core styles, which is the other way this was silently failing.
- Kept the existing scoped CSS rule (`.modal.mediavault-modal-shell .modal-close-button`) as a harmless secondary layer for the case where it does match; the JS lifecycle gate is now the actual fix.

## [4.41.0] — Root-Cause Fix for Modal Close Button

- **Actual root cause found**: every prior attempt (CSS descendant selector, per-modal `MutationObserver`, body-level `MutationObserver`) assumed `.modal-close-button` is nested *inside* `.modal` (`modalEl`), matching desktop's DOM shape. On Obsidian's mobile shell, the close button is not a descendant of `.modal` at all — it's rendered as a separate element inside the surrounding `.modal-container`, as a *sibling* of `.modal`. Every previous fix searched only inside `modalEl`'s own subtree, so on mobile it was searching a subtree the button was never actually in — it wasn't a timing or re-render problem, it was the wrong DOM assumption from the start.
- Replaced the nesting-based check with a structural one: for any `.modal-close-button` found anywhere in the document, walk up to its enclosing `.modal-container` and check whether that container also contains a MediaVault modal shell (`.mediavault-modal-shell`) *anywhere* within it — parent, sibling, or otherwise — rather than assuming a specific parent/child relationship. This only ever removes a close button that shares a modal container with one of our own modals, so Obsidian's native modals and other plugins' modals are untouched, and it works identically on desktop, Android and iOS without a platform check.
- Simplified the CSS fallback back down to the correct (desktop-shape) descendant rule only, since the mobile case is now handled correctly at the source instead of being CSS-guessed.
- `renderModalHeader`/`renderMobileBackButton`/`renderInlineBackButton` (used by all 15 header/back-button-bearing MediaVault modals) continue to be the single place this is wired up; `AddMediaModal`/`SelectMediaModal` are Obsidian `SuggestModal`/`FuzzySuggestModal` subclasses, which never render a close button, so they were correctly out of scope.
- Verification: `tsc -noEmit -skipLibCheck` clean, `eslint src` clean, production build succeeded. No `tests/` directory present (pre-existing gap); no new tests written, per standing instruction.

- New centralized `I18nService` (`src/i18n/`): single `t(key, params)` lookup used everywhere in the UI, with dot-notation nested keys, English fallback for any missing translation, and a `setLocale()`/`onChange()` subscription so already-mounted views can react to a language switch without an Obsidian restart.

## [4.7.0] — GDPR Import Matching Accuracy & Diagnostics

### Milestone 1 — Improve GDPR Import Matching Accuracy
- New `extractTitleMetadata()` (`services/importer/normalize.ts`): every imported title is now run through a full parenthetical-metadata extractor before TMDB search, not just a year-only regex. ### Milestone 2 — Investigate Missing Watch Time & Import Completeness
- Audited the full GDPR pipeline against a real TV Time export and found two real bugs:

## [1.2.0] — Modular TV Time importer

Replaced the single-strategy TV Time importer with a fully modular, extensible system supporting every TV Time export format and category, not just one JSON/CSV shape.

- **New `ImportManager`** (`services/importer/tvtime/manager.ts`) — auto-detects format (JSON/CSV) and export category, then dispatches to the matching importer. Adding support for a new TV Time export is one new module implementing `TVTimeImporter` plus one line registering it — nothing else changes.
- **Ten importer strategies**, each independently testable: `JsonMovieImporter`, `JsonSeriesImporter` (nested seasons/episodes), `JsonListImporter` (detects custom lists like "Costume C-Drama" and clearly labels them "not yet supported" rather than mis-importing them — list support is a planned follow-up), `CsvFollowedShowsImporter` (the `nb_episodes_seen`/`tv_show_name`/`is_favorited` shape), plus CSV importers for comments, likes, ratings, favorites, watched episodes, and watched movies
- **Common internal models** (`WatchImport`, `ReviewImport`, `LikeImport`, `RatingImport`, `FavoriteImport`) — the rest of the plugin never knows or cares whether data came from JSON or CSV
- **Comments** become watch-session or episode reviews, attached to an existing watch or creating one if needed — never overwriting a review that's already there
- **Likes** and **favorites** import as preserved metadata (`liked`/`likedAt` on episodes, `isFavorite` on media)
- **Ratings** fill in only if no rating exists yet — never silently overwritten
- **Duplicate detection** now matches in priority order: TVDB id → IMDb id → TV Time's own UUID → title+year → TMDB lookup (only for genuinely new titles, to avoid doubling API calls on a cancelled import)
- Import preview now shows the detected format/category up front (e.g. "CSV → Episode Comments") plus counts before anything is written; the post-import report breaks down movies/shows imported, episodes updated, comments/likes/ratings/favorites imported, duplicates merged, skipped, and errors

**Bug fixes found and fixed while wiring this up:**
- The importer redesign had been left mid-migration: `import-modal.ts` still referenced now-deleted files, and several modules in `services/importer/tvtime/` had relative import paths off by one directory level — the project didn't actually compile. Rewrote `ImportModal` to use the new `ImportManager`/`previewBundle`/`commitBundle` pipeline end-to-end, and fixed the path bugs.
- `parseJSON` rejected a single bare JSON object (exactly TV Time's real per-file movie/series export shape — not wrapped in an array or a `{movies, episodes, ...}` object), throwing "Unrecognized JSON structure" on genuine sample exports. Fixed to accept a bare object as one record.
- The "Favorites" filter in the library dashboard checked a status enum value that nothing sets anymore, rather than the `isFavorite` boolean the new importer (and everything else) actually uses — imported favorites were invisible to the filter. Fixed the filter and added a manual ★ favorite toggle to the media detail view (there was previously no way to set it by hand at all).
- 14 new/rewritten tests using the exact real-world sample JSON/CSV shapes provided, covering detection, parsing, full commit (including TVDB-id dedup on re-import and never-overwriting an existing rating)

## [1.1.0] — Automatic status system

Fixed a bug where every item stayed stuck on "Plan to Watch" regardless of actual watch progress. Status is now automatically derived and kept in sync everywhere.

- New centralized `StatusService.calculateMediaStatus()` — the single source of truth for status logic, replacing what would otherwise be scattered conditionals
- **Movies**: Plan to Watch (no sessions) → Finished (1+ sessions); stays Finished across rewatches
- **TV shows**: Plan to Watch (no watched episodes) → Currently Watching (some but not all released episodes watched) → Finished (all released episodes watched AND TMDB says Ended/Canceled) or **Waiting for New Season** (all released episodes watched but TMDB says Returning Series/In Production/Planned/Pilot)
- New `MediaItem.tvStatus` field capturing TMDB's raw show status, normalized from the TV details endpoint, to distinguish "done" from "more episodes coming"
- Manual overrides (Dropped, On Hold) are never overwritten by automatic recalculation
- Centralized through every mutation path: logging/deleting a watch (`watch-session-service.ts`), marking an episode or season watched (`episode-status-sync.ts`, replacing direct repository calls in the episode tracker UI), TV Time/CSV/JSON import, and Trakt sync — all now funnel through the same service, so there's exactly one place status logic can go wrong
- All views re-derive status from storage on their next read, so the library dashboard, media detail modal, and analytics reflect status changes immediately with no reload required
- 16 new tests covering every scenario from the spec: movie add/first-watch/rewatch/delete-all-sessions, TV plan-to-watch/currently-watching/waiting-for-new-season/finished (both by TMDB status and by "no remaining episodes"), unreleased-episode exclusion, and both manual overrides — plus fixes to 3 pre-existing test mocks that hadn't been updated for the new status-recalculation call inside `addWatchSession`/`deleteWatchSession`/`markEpisodeWatched`

## Known limitations

- No destructive "replace" import mode by design — it would conflict with the never-overwrite-reviews invariant. Import is always additive/merge.
- "Hidden gems" recommendations are a heuristic (next-tier TMDB affinity matches) rather than a true popularity-based signal, since TMDB's search/similar endpoints don't expose a popularity figure to filter on.
- Grid view (poster cards) is not virtualized — only the list view is. Grid is bounded by pagination instead; true grid virtualization with responsive column counts was judged not worth the added complexity at this stage.
